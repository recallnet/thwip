The reducer is the second net. Verified.
- **Claim 6 (two concurrent derivations) — nothing breaks.** Tree POSTs are content-addressed: identical deltas yield the same tree sha, idempotent. Commit POSTs differ only by timestamp, so two derivations make two unreferenced commits; one is pinned, the other is garbage-collectable. If both produced signed intents, only one can land — the first-parent check plus the fast-forward guard refuse the second.
- **Claim 3 (unreferenced commit is fetchable) — verified by the consumers' design.** The verify workflow checks out `candidateSha` directly (`.github/workflows/thwip-queue-verify.yml:34`) and the CLI does `git fetch --no-tags origin <sha>` (`packages/cli/src/candidate.ts:54`). Both rely on GitHub's upload-pack serving any object by full id — longstanding observed behavior, and the object's existence is guaranteed by the Git Data API create. The failure mode is a safe refusal (`CANDIDATE_UNAVAILABLE`), and both consumers verify `rev-parse HEAD^{tree}` against the pinned `candidateTreeOid` before running anything, so a wrong object refuses rather than passes.
- **Claim 2 (bail paths leave the lane as before) — verified for state, falsified for literal wording.** Every early return is the same `CANDIDATE_STALE` the caller already retries (`authorize-turn.ts:563-604`: attempt spent as `BASE_MOVED`, ordinal kept, bounded cooldown). No ref is ever created or moved. But "writes nothing" is false for the late bails: a bail after the tree POST, after the commit POST, or in the `catch` after a server-side create can leave an unreferenced tree or commit object. Invisible and harmless — the claim should read "leaves nothing referenced."

### Falsified claims

- **Claim 1 ("every merge engine agrees"; "precisely one tree any correct merge could produce") — falsified with real git (2.54.0, merge-ort).** Per-path forcing ignores the cross-path rename relationships ort tracks:
  - **rename/rename(1to2):** ancestor `{a.txt}`, base renames `a→b`, head renames `a→c`. `mergeTreeEntries` answers `{b.txt, c.txt}` — clean, the file duplicated at both destinations. `git merge-tree --write-tree` exits 1, `CONFLICT (rename/rename)`, and its conflicted tree carries `a.txt`, `b.txt`, and `c.txt` — a different tree and a conflict verdict. Reproduced locally; GitHub would report `mergeable=false`.
  - **rename/delete:** ancestor `{a.txt}`, base deletes it, head renames `a→c`. The code answers `{c.txt}`, clean. git exits 1, `CONFLICT (rename/delete)`. Reproduced locally.
  - **Criss-cross bases:** the compare endpoint returns one `merge_base_commit`; recursive/ort merges both bases into a virtual ancestor. Entry-level forcing on one real base declares clean what git conflicts on (e.g., `f=A` in base/ancestor-M1, `f=B` in head/ancestor-M2 → the code takes B; recursive conflicts via the virtual base).
  - What survives the attack: when git's own merge is *clean*, the entry-level answer equals it or the code bails (modify/rename crosses, modify/delete, D/F crosses all bail — the modify/delete and D/F bails have tests). The divergence is confined to cases git considers conflicts. The fix is cheap if wanted: bail when a path present in the ancestor is absent on exactly one side while the other side added a path carrying the same blob sha (rename heuristic), or narrow the doc to say the cleanliness verdict is weaker than git's for rename relationships.
- **Claim 4 ("mergeable===true is a fresh verdict") — not guaranteed.** `resolveCandidate` polls only while `mergeable` is null; a cached `true` computed against the old base is served as-is, and derivation's re-read has the same staleness window. The module header's own account ("mergeable recomputes to true") means a prompt GitHub recompute turns the rename-divergent cases into `mergeable=false` and derivation never fires — but that is GitHub's recompute lag, not a designed invariant. The claim is empirically load-bearing and unenforceable.
- **Claim 8 (wrong tree on main under `fast`) — possible, bounded.** Under `fast`, `requiresIntegratedRun` is false (`candidate-verdict.ts:25-27`): nothing executes the merged tree before the write. A rename/delete- or rename/rename-divergent tree pinned inside a stale-`mergeable` window passes every downstream guard, because the guards pin base, parents, and tree identity — never merge cleanliness. Lands on main. Bounded by three conjuncts (rename-crossing shapes × staleness window × fast profile), so low probability; under `fresh`/`remote` the suites run on the tree but would not catch a resurrected or duplicated file either.

### Notes

- `catch {}` (`derive-candidate.ts:275`) maps *all* failures — including a persistent 403 on the new writes — into endless retryable `CANDIDATE_STALE`. Fails safe, but quieter than this codebase's loud-failure style; a missing `contents: write` grant would present as a permanent stale cooldown.
